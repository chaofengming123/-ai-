# 第 31 课：检索评估，先判断有没有找到正确资料

上一课可以跨文档回答，但“能够返回文字”不代表检索效果好。本课增加一个人工标注与结果对照入口：提问前选择预期文档，检索后计算文档覆盖率和首个相关来源的排名。

本课不引入新模型，也不改变原有检索算法。先有可以对照的结果，后面调整检索方法时才知道是否改善。

## 一、操作一次

1. 更新前端，开发服务器运行时页面会自动更新；若没有启动，在 frontend 目录运行 `npm run dev`。本课后端代码未变，无需为本课重启后端。
2. 打开文档管理，选择上一课的练习知识库，确认两份练习文件已成功索引。
3. 输入“单个上传文件最多多大？”并在“检索评估”勾选 `upload-policy.md`。
4. 点击“查找相关片段”，观察覆盖率、排名和原文。
5. 输入“上传有什么限制，谁可以上传和提问？”，这次勾选 `upload-policy.md` 和 `access-policy.md`，重新检索。
6. 点击“生成知识库回答”，再对照原文检查回答。生成会重新检索，指标对应这次请求，不复用上次结果。

只有你阅读资料后确认相关的文件才应勾选。不要看完系统结果后再倒推“正确标注”，否则评估会失去意义。更改勾选不会修改旧结果，需要重新提交。

## 二、把问题拆成检索与生成两部分

```text
问题 → 检索片段 → 模型回答
         ↑           ↑
     有没有找对资料？ 是否正确使用资料？
```

比如文件明确写着上传上限 5 MB：

- 没找到这份文档：先检查索引是否可用、问题表达和检索排序。
- 找到文档，但片段里没有上限：继续检查分块和候选选择。
- 片段写了 5 MB，回答却说 10 MB：这是生成阶段的问题，不能单靠提高检索分数解决。

本课自动计算的是第一层“文档有没有出现”。第二层、第三层需要你阅读片段和答案判断。文件命中不能直接当作答案正确。

## 三、指标如何计算

设你人工标注了两份预期文档 A、B，最终最多三个片段来自 C、A、A。

| 指标 | 本课定义 | 示例 |
| --- | --- | --- |
| 预期文档覆盖率 | 出现在结果中的预期文档数 ÷ 标注文档数 | 1 / 2 = 50% |
| 首个预期来源排名 | 从 1 开始，首个来自预期文档的片段位置 | 2 |
| 倒数排名 RR | 1 ÷ 首个预期来源排名；未命中为 0 | 1 / 2 = 0.5 |

A 出现两次仍只算找回一份文档。排名沿用最终片段列表，不先按文档去重。没有标注时不计算指标，不把它显示为零分，也不据此推断“问题没有答案”。

覆盖率可以理解为本课标注集合上的文档召回比例。因为标注可能不完整，不能直接称为全库的真实召回率。RR 只表示这一条问题的倒数排名；多条问题的 RR 取平均才是 MRR，本课没有计算多题平均值。

这些值也不是 Qdrant 的相似度分数。相似度表示向量接近程度；这里的指标用人工标注判断结果是否命中预期来源。

## 四、关键代码：用 Set 避免重复计数

打开 `frontend/src/utils/retrievalEvaluation.js`：

```javascript
const foundIds = new Set(matches.map(hit => hit.documentId))
const found = expected.filter(doc => foundIds.has(doc.id))
const missing = expected.filter(doc => !foundIds.has(doc.id))
```

`map()` 从片段提取文档 ID；`Set` 去掉重复 ID；`filter()` 将预期文档分为已找回与未找回。使用 ID 而不是文件名，因为不同文档可以同名。

函数还用 `Map` 按 ID 去重标注，防止重复标注改变分母。覆盖率计算为 `found.length / expected.length`，在没有标注时提前返回 null，避免除以零。

```javascript
const firstIndex = matches.findIndex(hit => expectedIds.has(hit.documentId))
```

`findIndex()` 返回第一个匹配项的数组下标，下标从 0 开始，所以显示排名需要加 1。返回 -1 表示完全没命中，此时 RR 是 0，而不是拿 -1 参与除法。

这是一个纯计算函数：只接收片段和标注，返回结果，不调用接口，也不改变原数组。因此可以用固定输入检查边界条件，无需真实模型。

## 五、关键代码：请求开始时固定标注

`DocumentView.vue` 把已有文档列表通过 `:documents="documents"` 传给 `KnowledgeBaseAskPanel.vue`。子组件用复选框的 `v-model="expectedIds"` 保存勾选的 ID。

提交时先建立本次标注快照：

```javascript
const expectedDocuments = props.documents
  .filter(doc => expectedIds.value.includes(doc.id))
  .map(doc => ({ id: doc.id, fileName: doc.fileName }))
```

`map()` 创建新的对象，只保存 ID 和名字。这份列表随本次结果保留在浏览器内存中；你后来修改复选框，不会让已显示的旧请求分数跟着变化。

真正发送给后端的请求体仍只有：

```javascript
{ query: text }
```

`expectedDocuments` 是前端在响应后附加的字段，不发送给后端或模型。否则模型提前知道“标准来源”，就无法客观观察原检索流程是否找到它。

## 六、关键代码：computed 随本次结果计算

```javascript
const evaluation = computed(() => retrieval.value
  ? evaluateRetrieval(retrieval.value.matches, result.value.expectedDocuments)
  : null)
```

`computed()` 依赖当前响应，结果到达后自动重算。查找与生成两种响应都提供 retrieval；生成模式也使用 `retrieval.matches` 评估全部候选，而不是使用模型最终引用的 sources。

这样可以区分：系统找到了 A、B，但模型只引用 A。检索覆盖率应按 A、B 计算，是否遗漏 B 的事实要在生成阶段另行判断。

新请求开始时清空旧结果，处理中禁用重复提交与标注修改。继续使用已有 `createVectorStorage()` 的请求代次与会话版本检查；切换知识库通过组件 key 销毁旧状态。失败只显示错误，不生成虚假的零分评估。

本课没有评估历史或持久缓存，刷新后需重新标注。勾选文件不影响原来的权限检查、最多五份索引、跨文档去重和最终三个片段限制。

## 七、怎样设计有用的练习问题

先用下面的表手动记录，避免只挑系统容易答对的问题：

| 问题 | 预期文档 | 需核对的事实 |
| --- | --- | --- |
| 单文件最多多大？ | upload-policy.md | 5 MB |
| 上传完成就能问答吗？ | upload-policy.md | 还要手动建立成功索引 |
| 哪些用户可以上传？ | access-policy.md | 编辑者和管理员 |
| 上传限制是什么，提问要哪些权限？ | 两份文件 | 文件限制与三项权限 |
| 公司客服电话是多少？ | 不标注文档 | 原文未提供，应人工核对资料不足 |

最后一题不是自动“无答案评估”：不标注只表示没有可计算的参考集合。即使检索返回片段，也不代表这些片段能回答电话问题；这正是相似度检索与事实依据的区别。

先记录问题、标注、模型配置和索引版本，再记录覆盖率、RR、片段是否包含事实、回答是否符合原文。比较不同方案时使用同一批问题与资料，一次只改一个主要因素。两份很短的练习资料容易得高分，不代表真实企业文档同样有效。

## 八、边界与验证

预期文档如果未索引或模型不兼容，会显示在未参与列表，也会出现在未找回列表中。这是端到端的使用结果：先修复索引条件，再分析向量排序。不能为了让指标漂亮就把它从标注中悄悄删除。

最终最多三个片段，所以一次标注超过三份不同文档不可能全部覆盖。完全相同原文的去重也会只保留其中一个文件来源。理解这些规则后再解释分数，不能仅凭低分断言模型不行。

本课 37 项前端测试与生产构建通过。新增测试覆盖未标注、重复片段与标注、排名位置、零命中以及同名不同 ID 的文件。后端没有改动，本课未重跑后端测试，也未调用真实模型服务；实际使用检索按钮仍会按原流程调用 Embedding，生成按钮还会调用 GLM。
