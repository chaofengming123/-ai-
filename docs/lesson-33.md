# 第 33 课：候选重排，使用硅基流动 BGE Reranker

本课使用硅基流动专用重排模型 `BAAI/bge-reranker-v2-m3`，替换原先用 GLM 返回候选编号的方案。GLM 继续负责生成答案，重排默认关闭，开启后从最多六段候选中选出最多三段。

## 一、配置与运行

在本地 `docker/.env` 补充以下配置，保留已有数据库、Embedding 和 GLM 设置：

```dotenv
RERANK_ENDPOINT=https://api.siliconflow.cn/v1/rerank
RERANK_MODEL=BAAI/bge-reranker-v2-m3
RERANK_API_KEY=填写硅基流动API密钥
```

示例文件为 [重排配置](../docker/.env.rerank.example)。可以使用同一硅基流动账号已有的 Embedding API Key，但不能使用智谱 Key。三个组件的配置独立，便于以后分别更换模型或兼容服务，不自动借用其他组件的密钥。

2026-09-23 核对时，官方价格页将无 `Pro/` 前缀的模型列为免费；不要误选收费的 `Pro/BAAI/bge-reranker-v2-m3`。免费服务也可能限流，实际可用性以账号权限和平台状态为准。[官方价格页](https://siliconflow.cn/pricing)

本次已为当前 Mac 的本地配置设置地址、模型，并补齐重排密钥；该文件被 Git 忽略，不会推送。其他电脑独立运行后端时，需要在当地配置密钥。Windows 若共用 Mac 后端，只需更新并重启 Mac 后端。

停止原后端后启动新版，避免两份进程占用 8080。没有数据库迁移，也无需为更换重排模型重新建立向量索引。重排模型不改变 Embedding 的向量空间。

## 二、体验同一次请求的前后对照

1. 打开文档管理，选择已有成功索引的知识库。
2. 输入“上传完成后是否马上能问答？”，预先勾选包含答案的文档。
3. 可以使用向量或混合检索；混合模式继续填写关键词，例如“索引”。
4. 勾选“启用 BGE 重排”，点击查找相关片段。
5. 展开重排前的前三段，对照最终片段和前后的覆盖率、RR。
6. 点击生成知识库回答，核对答案使用了哪些来源。

只有两份很短的文件时，可能只是顺序变化，覆盖率并不改变。模型重排也不保证比原检索更好。

## 三、三个模型各自的作用

| 组件 | 默认模型 | 作用 |
| --- | --- | --- |
| Embedding | BAAI/bge-m3 | 将问题或文档转成向量 |
| Reranker | BAAI/bge-reranker-v2-m3 | 比较问题与候选原文的相关性 |
| 回答模型 | glm-4.7-flash | 根据最终片段生成答案 |

RRF 只合并两路排名，重排则提交问题和真实候选文本供模型判断。重排只能选择已召回候选；正确片段未进入候选池时，重排无法补救。

现在的重排接口接收 `query` 与 `documents`，返回带 `index` 和 `relevance_score` 的 results；不是 Chat Completions，不发送 system/user 消息，也不让模型生成排序 JSON。[硅基流动 Rerank API](https://docs.siliconflow.cn/docs/api/rerank-post)

## 四、完整执行顺序

```text
Vue：问题、检索方式、关键词、rerank 开关
 → Security 检查知识库查看、文档查看和 AI 对话权限
 → Controller 把 JSON 绑定为 Query record
 → Service 校验配置与参数
 → 向量或混合检索
 → 原文去重，开启重排时取最多六段
 → 保存原前三段 baseline，并检查版本
 → RerankClient 调用硅基流动
 → 验证返回下标、分数、数量和顺序
 → 下标映射到服务器原候选，再检查版本
 → 重新分配 sourceId，返回片段和前后对照
 → 若要求生成：GLM 回答、引用检查、版本检查后返回
```

关闭开关时继续原前三段流程。开启但候选少于两段时跳过重排调用；开启选项仍先要求重排配置完整。只查找加重排不要求 GLM 配置，生成回答才要求 GLM。

## 五、关键代码：独立客户端与请求体

`RerankClient` 是 Spring 的 `@Component`，通过配置注入 endpoint、model、key 和超时。远程地址要求 HTTPS，HTTP 回环仅供本地模拟测试；不跟随重定向，避免把认证信息带到其他地址。

关键请求内容是：

```java
Map.of("model", model, "query", question,
       "documents", texts,
       "top_n", Math.min(3, texts.size()),
       "return_documents", false)
```

documents 是候选原文列表，最多六段、每段最多八百个 UTF-16 字符。top_n 要求返回最多三个结果。return_documents=false 避免重复返回原文，应用本来就保存着可信的候选列表。认证通过后端的 Bearer API Key 完成，浏览器拿不到密钥。

这里最多发送四千八百字符原文，问题另限一千字符；字符数不等于 token 数。客户端复用有响应体大小限制的接收器，并设置 45 秒超时。超时、网络故障、限流或错误响应会明确报错，不自动换模型、重试或回退原排名。

## 六、关键代码：零基下标与结果验证

服务商返回的 index 从 0 开始。例如：

```json
{
  "results": [
    {"index": 5, "relevance_score": 0.92},
    {"index": 3, "relevance_score": 0.81},
    {"index": 0, "relevance_score": 0.63}
  ]
}
```

这表示原候选列表第六、第四、第一段，按此顺序输出。以上数值是示例，不是实测分数。

`decode()` 检查 results 数量必须等于 `min(3,候选数量)`；index 必须是范围内、不重复的整数；relevance_score 必须是有限数值，并按非递增顺序返回。不能把缺结果、重复结果或非法分数当成一次正常重排。

服务返回的 document 字段即使存在也不会用于覆盖服务器原文。Service 的关键映射为：

```java
var indices = reranker.select(question.strip(), pool.stream().map(Hit::text).toList());
selected = numbered(indices.stream().map(pool::get).toList());
```

因为 index 已经从 0 开始，直接 pool.get(index)，不能像旧的 1 基编号方案一样减 1。numbered() 再从 1 开始分配最终 sourceId。

所以原下标 5 成为最终来源 1 时，回答引用 sourceId=1，服务器应返回原第六段。文档 ID、块编号、文件名、字符范围和原文都由应用自己的数据决定。

## 七、保留原分数，区分排名与概率

客户端检查 relevance_score 后使用服务返回的排名；目前没有把它加入页面 DTO。页面保留重排前的向量相似度或 RRF 分数，并明确标注“重排前”。

因此最终列表里的旧分数可以不再递减，不代表程序排序出错。不同类型分数不能直接比较，也不能解释为答案正确的概率。本课没有按重排分数设资料不足阈值；是否足以回答仍由后续问答判断，并需要人工核实。

## 八、Vue 与 baseline 的作用

`rerank` 请求字段默认 false。后端返回 enabled、applied、model、candidateCount 和 before，分别说明是否开启、是否实际执行、模型、候选数和原前三段。

前端对 before 与最终 matches 分别调用 `evaluateRetrieval()`，使用同一份请求时的预期文档标注。baseline 不重新检索，所以比较不会受到第二次召回变化影响。标注不发送给重排模型。

切换知识库会清理旧状态，正在处理时阻止重复点击。页面显示响应里的模型与方式，后续改变勾选不会改写旧结果。评估仍只衡量文档覆盖和位置，不自动证明片段能支持答案。

## 九、调用次数与版本检查

假设候选至少两段且流程成功：

| 操作 | 重排 API | GLM |
| --- | --- | --- |
| 查找，关闭重排 | 0 | 0 |
| 查找，开启重排 | 1 | 0 |
| 回答，关闭重排 | 0 | 1 |
| 回答，开启重排 | 1 | 1 |

不足两段跳过重排；没有片段也跳过答案生成。候选原文送到硅基流动重排，最终最多三段再送智谱生成答案。

处理期间发布新索引，返回 409，不继续使用过期候选生成回答。并发名额覆盖整个请求，finally 保证失败也释放。前端仍最多等 300 秒，各上游调用有独立超时，这不是统一的服务器截止时间。
