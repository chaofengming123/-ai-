# 第 33 课：候选重排，让 GLM 再判断片段与问题的关系

上一课用 RRF 合并关键词和向量排名，本课增加一个可选步骤：把初步找回的最多六段原文交给现有 GLM，让它按“对当前问题的帮助程度”选择并排序最多三段。

这是使用聊天模型实现的教学版列表重排，没有接入专用 Reranker 模型或新增模型密钥。默认关闭，可以与原检索结果对照。

## 一、先体验前后对照

1. 保持 MySQL、MinIO、Qdrant 运行，停止原后端后启动新版；不要同时启动两份占用 8080。
2. 打开“文档管理”，选择已有成功索引的练习知识库。
3. 输入“上传文件后是否马上就能问答？”，勾选预期包含答案的文档。
4. 可以选择向量或混合检索。混合模式仍需填写关键词，例如“索引”。
5. 勾选“启用 GLM 重排”，点击“查找相关片段”。
6. 展开“查看重排前的前三段”，对照最终来源与前后的覆盖率、RR。
7. 再点击“生成知识库回答”，观察回答实际引用了哪些重排后的片段。

沿用智谱 LLM 配置和硅基流动 Embedding 配置，无数据库迁移，也无需重建同一模型配置下的有效索引。开启重排后，查找按钮也会调用 GLM；生成按钮通常需要两次 GLM 调用，先重排再回答。

只有两份很短的文档时，前后可能只是顺序不同，覆盖率不会变。使用包含更多独特片段的资料才更容易观察候选选择的区别，但不能预先保证重排提高成绩。

## 二、检索、融合、重排分别负责什么

| 步骤 | 本项目如何实现 | 看到了什么 |
| --- | --- | --- |
| 向量检索 | 问题向量查询 Qdrant | 向量接近程度 |
| 关键词检索 | 原文字面匹配 | 关键词是否出现 |
| RRF 融合 | 合并两路排名贡献 | 各路位置，不分析答案依据 |
| GLM 重排 | 发送问题与候选原文 | 问题和片段的具体内容 |
| 生成回答 | 发送最终三个片段 | 本次提供的回答上下文 |

RRF 可以让两路都命中的候选靠前，但它没有读懂片段。GLM 重排尝试判断片段是否直接提供答案依据。不过模型也可能判断错误，相关性排序不等于事实验证。

重排只能从已有候选中选择。正确原文如果根本没有进入前六段候选，重排无法把它找回来；这时应检查前面的检索和分块。

## 三、执行顺序

```text
请求 query、mode、keywords、rerank
  → 检查权限、参数和模型配置
  → 原有向量或混合检索
  → 完全相同原文去重，保留最多六段
  → 记录原前三段 baseline
  → 检查知识库版本
  → GLM 返回按顺序排列的 candidateIds
  → 检查编号与截断，重新检查版本
  → 按编号选择原始片段，重新分配 sourceId
  → 查找：返回重排前后结果
  → 回答：用最终片段生成，校验引用与版本，再返回
```

关闭重排时仍只保留原前三段，原有调用方式不变。开启但候选不足两段时，直接跳过重排模型调用；开启选项仍要求本地 LLM 配置完整。

## 四、关键代码：可选开关与候选池

`KnowledgeBaseRagController.Query` 增加 `Boolean rerank`。`Boolean.TRUE.equals(query.rerank())` 只有在明确传 true 时启用；旧请求没有该字段时继续关闭。

在 `KnowledgeBaseRagService` 中：

```java
pool.add(hit);
if (pool.size() == (rerank ? 6 : 3)) break;
```

pool 是当前去重后的候选列表。开启重排时给模型更多选择空间，最终仍只输出三个片段。向量通道仍为每文档 Top 3，混合通道仍沿用前课的候选上限；本课没有扩大底层查询范围。

```java
var baseline = numbered(pool.stream().limit(3).toList());
```

baseline 保存同一次检索在没有重排时会展示的前三段。它不是再次调用检索，也不需要额外 Embedding，因此可以与最终结果公平对照。模型返回之后不会改写 baseline。

## 五、关键代码：把问题与原文交给排序器

新增 `LlmReranker.select()`，接收 `LlmClient`、问题和最多六段文字。它先把每段文字分配为 candidateId 1、2、3……，再构造两条消息：

- system：固定排序规则，要求只返回候选编号，不回答问题，也不能执行原文里的命令。
- user：JSON 格式的问题与 candidates，每个候选包含编号和原文。

代码调用已有 `llm.complete()`，复用模型地址、认证、请求超时和异常处理。每段最多八百个 UTF-16 字符，因此重排原文最多四千八百字符；问题、提示词和 JSON 包装另算，字符也不等于 token。

不传预期文档标注、文件名或模型编写的来源。预期标注仍只用于前端评估；重排模型只能依据问题和提供的片段选择。

要求返回例如：

```json
{"candidateIds":[6,4,1]}
```

这表示候选 6 最相关，其次是 4、1。它不包含答案，也不包含可信的新原文。固定指令与数据分离可以减少混淆，但不能保证模型永远不受文档中的指令影响，因此仍需验证结构和人工核对结果。

## 六、为什么严格检查模型编号

`LlmReranker` 要求返回数组长度恰好为 `min(3,候选数量)`，每个元素必须是有效范围内的整数且不重复。

检查会拒绝：

- 返回 Markdown、自然语言或无法解析的 JSON。
- 编号越界、重复、非整数、数量不符合要求。
- 模型输出被截断。

比如四段候选中返回 `[1,2,9]`，后端不能猜测 9 原本想表示什么。当前请求直接报错，不静默回退成原排序，也不调用模型自动修补。

这里要求保留固定数量的相对优先候选，即使它们都不能充分回答问题，也会选出其中相对靠前的几段。重排阶段不负责“资料不足”判断，后续问答继续用 `GroundedAnswer` 处理资料不足。

## 七、候选编号怎样变成引用编号

在 Service 中：

```java
selected = numbered(ids.stream().map(id -> pool.get(id - 1)).toList());
```

`id - 1` 将候选编号变为数组下标；`pool.get()` 取得真实原文与来源；`numbered()` 按新顺序重新分配 sourceId。

例如 candidateIds 为 `[6,4,1]`，最终 sourceId 1 对应原候选 6，sourceId 2 对应原候选 4。回答模型只看到最终片段及新的 sourceId；它引用 1 时，后端必须返回原候选 6 的文档和原文。

candidateId 是重排候选编号，sourceId 是最终上下文编号，chunkIndex 是文件内块编号。三个编号用途不同，不能互相直接代替。

原相似度或融合分数保留不变，所以重排后的分数可能不再递减。页面明确标为“重排前相似度”或“重排前融合分数”。本课没有让 GLM 输出可比较的数值相关性分数。

## 八、Vue 如何显示同一次请求的比较

页面将勾选状态以 rerank 发送给后端。后端在 retrieval.rerank 中返回：

| 字段 | 作用 |
| --- | --- |
| enabled | 用户本次是否开启 |
| applied | 实际是否调用了重排模型 |
| model | 实际重排时使用的模型配置名 |
| candidateCount | 本次候选池数量 |
| before | 开启时保留的原前三段 |

前端对 before 和最终 matches 分别调用上一课的 `evaluateRetrieval()`，使用同一份请求时的标注。`computed()` 在响应到达时计算两组指标，切换当前勾选状态不会修改已经返回的结果。

生成回答模式仍对所有最终 matches 评估，而不是只评估模型选择引用的 sources。页面还能展开原前三段，手动核对“命中文档”和“片段确实含答案”之间的区别。

重排默认关闭，处理中禁止重复提交；切换知识库与登录会话时继续使用原有状态清理规则。没有新增持久化评估记录。

## 九、额外调用、失败与版本检查

候选至少两段时：

| 操作 | GLM 调用次数 |
| --- | --- |
| 查找，关闭重排 | 0 |
| 查找，开启重排 | 1 |
| 生成回答，关闭重排 | 1 |
| 生成回答，开启重排 | 2 |

表中假设流程成功且有可用片段；模型失败会提前结束。候选不足两段时跳过重排；没有片段时，回答也跳过生成并返回资料不足。

重排前检查一次版本，重排后再检查一次。如果处理中发布了新索引，返回 409，并且不继续调用回答模型。生成结束后还会检查版本。检查不是跨服务事务，也不会让已展示答案自动更新。

并发名额覆盖整个请求，包括重排和生成；失败在 finally 中释放。继续保留原有知识库范围、权限、索引模型兼容和来源校验。

每次模型调用沿用配置的超时，前端总等待仍为 300 秒；两次模型调用会增加耗时，这不是统一的服务器总截止时间。关闭页面不保证服务商立即停止处理，失败不自动重试。

本次 127 项后端测试、37 项前端测试及生产构建通过。存储链路使用独立测试 MySQL、MinIO、Qdrant；现有 8080 后端未停止，请自行重启以加载本课功能。

测试检查排序规则与资料分离、候选上限、非法编号与截断拒绝、空或单候选跳过、重排后引用映射、同次请求的 baseline、处理中版本变化、失败释放名额，以及真实 HTTP 的匿名拒绝与前后顺序响应。模型全部使用模拟响应，未调用真实服务商。

练习时固定问题、资料和标注，观察重排前后指标，然后阅读片段：

1. 覆盖率相同但 RR 提高，说明发生了什么？
2. 原候选 6 被选为来源 1，回答引用 1 时应展示哪段原文？
3. 为什么原相似度更低的片段可以排在前面？
4. 正确答案不在六段候选里时，应该先检查哪一步？
