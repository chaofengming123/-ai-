# 第 35 课：问题向量缓存，观察命中与失效

上一课显示各阶段耗时，本课开始减少重复计算：同一用户在短时间内提交相同问题时，复用已有问题向量。只缓存问题向量，文档检索、版本检查、重排和答案仍每次执行。

## 一、先运行一次

1. 重启新版后端，打开文档管理，选择已有兼容成功索引的知识库。
2. 输入一个问题，暂时关闭重排，点击查找相关片段。
3. 页面显示“未命中：已生成并缓存”。展开耗时，问题向量生成应执行一次。
4. 在五分钟内保持问题不变，再查找一次，应显示“命中：复用问题向量”，向量生成次数变为零。
5. 勾选“本次跳过问题向量缓存”，再查一次，观察重新生成的耗时。
6. 取消勾选后仍可命中原缓存，前提是它尚未过期或被容量淘汰。

本课使用后端进程内存，不需要 Redis、新配置或数据库迁移。后端重启会清空缓存。没有参与检索的文档时不需要问题向量，页面显示“未使用”。

## 二、缓存究竟保存了什么

缓存保存问题对应的数值数组，不保存答案、候选原文或知识库检索结果。一次命中只省去问题 Embedding 请求。

```text
权限与索引条件检查
 → 构造缓存键
 → 命中：取向量副本
 → 未命中：调用 Embedding → 保存成功向量 → 取副本
 → 继续读取当前文档索引并检索
 → 可选重排与生成回答
```

因此文档发布了新索引后，可以复用同一个问题向量，再对新索引检索。它不会因为命中问题向量就返回旧答案。单文档检索入口和向量实验页本课尚未接入该缓存。

## 三、关键代码：缓存键为什么有三个部分

`QuestionVectorCache` 中定义：

```java
private record Key(long userId, String space, String questionHash) {}
```

userId 隔离不同用户。space 来自已有 `embedding.spaceId()`，由服务地址和模型共同决定，避免不同模型生成的向量混用。questionHash 是去掉两端空白后问题的 SHA-256 摘要。

不转小写、不移除内部空格，也不把相似措辞视为同一个问题。“q”和“ q ”共用缓存，“q”和“Q”分别缓存。这与实际传给 Embedding 的 strip() 处理保持一致。

摘要使缓存键不直接保存原问题文字，但它不是加密；对于可猜测的短问题，摘要不能提供强保密性。缓存仍属于应用内存数据，应随正常的后端访问控制保护。

键不含知识库 ID，因为问题向量与被检索的库无关。同一用户切换知识库、检索方式或开关重排时可以复用向量，但每次仍检查权限和索引条件。键也不含密钥，轮换密钥不改变数学向量空间；当前配置由启动时加载，重启本身会清空缓存。

## 四、关键代码：五分钟有效期

每条 Entry 保存向量副本和成功计算完成后的 created 时间。读取时使用单调计时差值检查：

```java
now - entry.created() >= ttl
```

达到五分钟就视为过期，不能再命中。命中不会延长有效期，所以一直提问也不会让旧向量永久存活。

当前实现采用读取时清理：普通缓存访问先删除过期项。没有请求时，过期对象可能仍在内存里，但下一次访问不会复用它；本课没有后台清理线程。缓存容量始终有上限。

## 五、关键代码：容量和最近使用顺序

缓存使用带访问顺序的 LinkedHashMap：

```java
new LinkedHashMap<>(16, .75f, true)
```

最后的 true 表示访问条目时会更新顺序。最多保存 128 条，写入超过限制时移除最久未使用的条目，即 LRU 淘汰。容量是整个后端进程共用的上限，不是每人 128 条。

所以五分钟是最长可复用时间，不承诺五分钟内必然命中：容量淘汰和后端重启也会导致未命中。不同用户的数据不互相复用，但会竞争这一总容量。

## 六、为什么网络调用放在锁外

LinkedHashMap 本身不能被多个请求随意并发修改。代码在读缓存、清过期项和写入时使用 synchronized(entries)，保证这些短操作互斥。

```java
var vector = load.get().clone();
```

计算向量的 load.get() 放在锁外，避免一个请求等待网络时，让其他用户连缓存读取都无法进行。当前知识库 Service 已限制同一用户同时一个请求，因此通常不会出现同用户同键的重复计算。

缓存类本身没有实现“同键并发只计算一次”的合并机制；如果以后在其他并发入口复用它，需要另行设计。多个后端实例也各自有独立缓存，本课没有分布式一致性。

## 七、为什么向量要复制

Java 数组是可修改对象。把缓存里的数组直接交出去，调用者改一个元素就会污染后续请求。

本课在写入和返回时使用 clone()：保存自己的副本，命中时也返回新副本。原模型返回数组或某次调用拿到的数组被改动，不会改变缓存内部数据。

只有 Embedding 成功返回的向量才写入缓存。网络失败直接抛出，错误不会缓存；如果向量成功而后面的检索失败，成功向量仍可保留供后续请求使用。

## 八、跳过缓存不是刷新缓存

请求增加可选的 bypassCache，默认 false。开启后不读也不写缓存，直接计算本次向量并标记 BYPASS。它不会清除或替换原条目，用于观察未缓存路径。

| 状态 | 含义 |
| --- | --- |
| HIT | 使用缓存向量 |
| MISS | 无有效条目，已计算并保存 |
| BYPASS | 用户主动跳过读写缓存 |
| NOT_USED | 没有可参与检索的文档，无需向量 |

错误响应仍只显示错误，不展示虚构的缓存状态。若服务商在同名模型下更新行为，五分钟内可能复用旧向量；可跳过缓存观察，或重启后端清空缓存。长期部署需要更明确的模型版本管理。

## 九、和耗时统计怎样配合

Service 把上一课的 EMBEDDING 计时放在缓存提供的加载函数内部：

```java
var cached = vectorCache.get(userId, embedding.spaceId(), question, bypassCache,
    () -> timings.measure(RagTimings.Stage.EMBEDDING,
        () -> embedding.embed(List.of(question.strip())).get(0)));
```

命中时不会执行 Lambda，所以向量生成计数为零。缓存查询、哈希和数组复制属于其他处理时间。文档检索次数不因缓存命中而减少。

Vue 用服务端返回的 embeddingCache 显示本次状态，不凭请求耗时猜测命中。“第二次更快”本身不能证明命中，应结合状态和执行次数判断。
