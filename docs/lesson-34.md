# 第 34 课：检索耗时统计，看清时间花在哪里

前面已经实现向量检索、混合检索、BGE 重排和 GLM 回答。本课在知识库结果里加入“本次耗时”，显示各阶段执行次数与累计时间，为后续判断哪些重复工作值得缓存提供依据。

## 一、先看一次结果

1. 重启新版后端，保留已有 MySQL、MinIO、Qdrant 与模型配置。
2. 打开文档管理，选择至少两份文档已成功索引的知识库。
3. 输入问题，先用向量检索，关闭重排，点击查找相关片段。
4. 展开结果里的“本次耗时”，观察问题向量生成和文档检索。
5. 切换混合检索、填写关键词，再查一次，观察关键词扫描。
6. 开启 BGE 重排，再生成知识库回答，观察重排和生成两个阶段。

每次点击仍会实际执行对应流程，不自动批量测试。本课没有加入缓存，也没有数据库迁移或模型变更，不需要重建索引。

## 二、为什么先统计再优化

如果一次回答等待十秒，可能是向量服务慢、文档查询多、重排耗时，也可能主要在等待 GLM。只看浏览器总等待，无法判断应先改哪一段。

本课返回五个阶段：

| 阶段 | 计时范围 | 执行次数含义 |
| --- | --- | --- |
| 问题向量生成 | EmbeddingClient 调用及响应解析 | 本次通常一次 |
| 文档向量检索与校验 | 单文档 searchWithVector，包括数据库、Qdrant 与来源检查 | 每份参与文档一次 |
| 关键词原文扫描与校验 | 单文档 scanForKeywords | 混合模式下每份参与文档一次 |
| BGE 重排 | RerankClient 调用与响应检查 | 开启且至少两段候选时一次 |
| GLM 生成与格式校验 | GroundedAnswer 生成及结构、引用编号校验 | 有候选且要求回答时一次 |

一次“文档向量检索”内部可能访问多次存储，所以阶段次数不是 HTTP 请求总数。关键词匹配、排序融合等未被以上计时块包围的工作计入“其他处理”。

## 三、完整执行顺序

```text
进入 KnowledgeBaseRagService → 创建本次计时器
  → 校验参数与配置，查参与文档
  → 测量问题 Embedding
  → 循环测量每份文档检索／扫描
  → 排序、去重、版本检查
  → 可选：测量 BGE 重排
  → 可选：测量 GLM 生成与格式检查
  → 最终版本检查
  → 生成计时快照 → 和业务结果一起返回 Vue
```

计时没有改变原有调用顺序、权限、模型或索引版本检查。查找与回答都把统计放在 retrieval 对应的结果中；回答模式的统计在生成完成后才取快照，包含本次生成时间。

## 四、关键代码：每次请求创建自己的计时器

Service 入口新增：

```java
var timings = new RagTimings();
```

它是方法里的局部对象，不是 Service 的共享字段。两个用户同时提问时，各自持有独立计数，避免把甲的重排时间加到乙的请求里。

`RagTimings` 使用 `System.nanoTime()` 的差值测量经过时间，不用日期时间来计算时长。它测到的是包含等待在内的耗时，不是线程实际消耗的 CPU 时间。纳秒单位也不表示测量一定具有纳秒级精度。

## 五、关键代码：用 Supplier 包住一个阶段

例如问题向量生成：

```java
var vector = timings.measure(RagTimings.Stage.EMBEDDING,
    () -> embedding.embed(List.of(question.strip())).get(0));
```

`() -> ...` 是 Lambda，表示一段暂时交给 measure 执行的工作。`Supplier<T>` 是“无输入、返回一个 T 类型结果”的函数接口；这里 T 是向量数组类型。

measure 的核心实现：

```java
long begin = clock.getAsLong();
try {
    return work.get();
} finally {
    nanos[stage.ordinal()] += clock.getAsLong() - begin;
    calls[stage.ordinal()]++;
}
```

`work.get()` 执行业务并保留返回值；`finally` 在成功或抛异常时都会累计时间与次数。它不会吞掉异常，失败仍走原来的错误响应，不会变成成功结果。

Stage 是固定枚举，ordinal 对应两个数组中的位置。数组只用于同一请求的内部累计，不写入数据库，也不依赖用户输入的阶段名字。

## 六、为什么多文档耗时要累加

每份文档检索都调用一次 measure(VECTOR_SEARCH, ...)。假设两份分别花 30 ms 和 50 ms，该阶段显示 2 次、80 ms，而不是只保留最后一次的 50 ms。

当前文档处理是顺序执行的，计时块也不嵌套，因此可以把五个阶段时间相加，从总时间中减去它们得到其他处理时间。

如果以后改成并行查询，多个阶段可能同时进行，累计耗时可能超过总经过时间。届时必须调整统计解释，不能原样套用现在的相减逻辑。本课的计时器不是通用的并发追踪系统。

## 七、计时快照与显示精度

`snapshot()` 生成不可变 Report，包括 totalMillis、otherMillis 和 steps。每项 Step 包含 stage、calls、millis；输出不会包含密钥、请求正文或模型响应原文。

内部先累计纳秒，再统一转换为整毫秒。因此发生过的操作如果不足 1 ms，会显示“1 次、0 ms”；从未执行的操作是“0 次、未执行”。不能把两者理解成同一回事。

每项都单独向下取整，所以显示的分项毫秒之和与总毫秒可能差少量毫秒。这是显示精度差异，不应人为补到某个模型阶段。

其他处理包括初始配置与数据库读取、关键词匹配、融合去重、阶段外版本检查以及少量本地代码执行。它不是单纯的数据库耗时。

## 八、Vue 如何展示

`KnowledgeBaseAskPanel.vue` 从 `retrieval.timings` 读取报告，用 `v-for` 展示固定阶段，`stageLabels` 把后端枚举名称转为中文。使用 details 折叠面板，让耗时信息随实际结果保存，不影响主要答案阅读。

后端总时间从业务方法开始，到结果构建时取快照为止，不含此前的认证过滤、浏览器网络传输、后续 JSON 序列化、渲染和部分返回收尾。因此它不等于浏览器开发者工具里的完整请求时间。

旧后端没有 timings 字段时面板不显示，需重启新版才能看到。失败时继续显示错误，不展示这次部分统计，也不会沿用上一条成功结果冒充本次报告。

## 九、如何用这些数据思考缓存

连续手动提交同一问题，观察向量阶段仍执行一次，这说明当前尚未缓存问题向量。但第二次更快不必然代表缓存命中，网络波动、连接复用和服务负载都可能影响耗时。

后续缓存设计要先明确复用对象和失效条件。例如问题向量与问题文字、Embedding 地址和模型有关；检索结果还与文档成员及索引版本有关。缓存答案则涉及更多条件，不能只用问题作为键就长期复用。

本课先收集单次观察，不输出“平均耗时”或“P95”等多样本统计，也没有性能优化结论。用相同问题和资料多次观察时，应同时检查检索质量，避免为了快而遗漏正确片段。

## 十、验证与练习

本次 131 项后端测试、37 项前端测试及生产构建通过。使用独立测试 MySQL、MinIO、Qdrant 和模拟模型；现有 8080 后端未停止，请自行重启加载本课功能。

单元测试通过注入假的时钟推进时间，不使用 sleep 来断言精确毫秒。测试验证多次累计、其他处理、异常继续抛出、旧快照不改变，以及不足一毫秒与未执行的区别。

真实 HTTP 业务测试检查检索、扫描、重排和生成的调用数量；无可用索引时各模型阶段应为零。模型使用模拟响应，因此自动测试结果不是实际服务商的速度评测。
